# TRACE 评测细则（trace-evaluation）

来源：SkillHub 联合玄武实验室发布的 TRACE 评测体系（介绍文章：https://developer.cloud.tencent.com/article/2698657 ）。SKILL.md 第四步给出框架与流程，本文件给出每个维度的检查细则、判定标准与轮次记录模板。执行第四步遇到判定争议、或需要输出正式检查报告时读本文件。

## 判定标准

每个维度只有两档结论，且必须附证据：

- **通过**：该维度所有检查项均满足，能引用行号、命令输出或文档位置作证。
- **整改**：任一检查项不满足，写明不满足的项、证据、修复方案。

不接受无证据的「通过」；不确定的项按「整改」处理并标注「需人工确认」。

## 五维检查细则

### T 可信任度——值得信任吗

| 检查项 | 通过标准 |
|---|---|
| 内容安全 | 无恶意代码、注入指令、诱导外传数据的表述 |
| 最小权限 | allowed-tools 只申请必需工具；未声明则视为满足 |
| 敏感信息 | 不收集、不明文记录、不外传敏感数据 |
| 国内可用 | 依赖的服务国内可访问；GitHub 属可用但不稳定，需有降级路径 |
| 中文支持 | 中文用户可全程用中文使用该技能 |

### R 可靠性——稳定可靠吗

| 检查项 | 通过标准 |
|---|---|
| 命令可运行 | 正文所有命令语法正确；关键命令实跑验证过 |
| 结果一致 | 相同输入走相同路径产出一致，不依赖随机或当前时间 |
| 边界输入 | 空输入、超长输入、特殊字符、路径含空格等有处理或明确报错 |
| 异常反馈 | 失败时给出可读的中文错误与下一步建议，不静默失败 |
| 管线与门禁 | 含门禁/校验脚本的已构造必红用例证明能失败；多脚本管线的中间产物有下游消费者 |

### A 适用性——适配场景吗

| 检查项 | 通过标准 |
|---|---|
| 场景匹配 | 功能与 description 声称的场景一致，不夸大 |
| 触发清晰 | 读 description 即可判断该用/不该用；正例触发、负例与近邻不触发（用 evals/trigger_cases.json 核对） |
| 能力边界 | 明确写出不做什么（Exclude 或正文边界声明） |
| 输入输出 | 输入要求与输出格式均有定义 |

### C 规范性——合乎规范吗

| 检查项 | 通过标准 |
|---|---|
| 渐进式披露 | metadata → SKILL.md → references 三级合理，深度内容已下沉 |
| 结构清晰 | 章节层次分明，目录名 = name，SKILL.md 少于 500 行 |
| 限制说明 | 前置条件、平台差异、已知限制写全 |
| 示例充分 | 命令有 bash 块、可枚举事实有表格、验收有清单，典型场景有示例 |

### E 有效性——效果好吗

| 检查项 | 通过标准 |
|---|---|
| 结果正确 | 按技能执行能得到正确产出（以 GREEN 复跑的行为证据为准，协议见 behavioral-eval.md） |
| 输出完整 | 每一步的产物齐全，无半成品 |
| 可直接使用 | 产出无需大量人工修改即可用 |
| 真实增益 | 相比无技能基线确有提升，证据是第一步记录的基线失败点在 GREEN 复跑中全部消失 |

## 四项重点映射

| 重点 | 归入维度 |
|---|---|
| 定义清晰性 | A（触发与边界）+ description 质量 |
| 结构完整性 | C（章节与资源结构） |
| 格式一致性 | C（frontmatter、目录、行数符合所在生态规范） |
| 可执行性 | R + E（命令可跑、步骤可照做） |

## 轮次记录模板

每轮全量复查记一行，交付时并入第五步的 TRACE 检查报告：

```markdown
| 轮次 | T | R | A | C | E | 整改项 | 证据 |
|---|---|---|---|---|---|---|---|
| 1 | 通过 | 整改 | 通过 | 整改 | 通过 | R:命令健壮性；C:补示例 | validate_skill.py exit 0；行数 183 |
| 2 | 通过 | 通过 | 通过 | 通过 | 通过 | 无 | 校验器 exit 0；边界测试通过 |
```

## 局限性

C 维度的「结构清晰」「示例充分」与 E 维度的「真实增益」带主观性，以对抗审查（见 behavioral-eval.md）加人工复核为准；评测结论随技能版本迭代失效，修改后须重跑全量复查。
