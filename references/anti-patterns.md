# 反模式与 FAQ（避坑详解）

何时读：首次执行本 Skill 的恢复流程前，以及遇到 FAQ 覆盖的边界情形（相似度计算方式、阶段缺失、重试用尽、并发惊群）时。

## 常见反模式（禁止）

- ❌ 对最终动作（付款/部署/删库）做自动重试
- ❌ 仅按进度百分比判断是否恢复（应基于错误类型）
- ❌ 相似度未达阈值就熔断（会漏掉真实新错误；阈值数值以 SKILL.md 的 Core Principles 与 Retry Policy 为准，本文件不重复数值）
- ❌ 对可覆盖重提交的 media 任务先执行撤销（浪费时间；仅当平台明确残留脏数据或重复计费时才需先清理失败产物）
- ❌ 静默吞掉致命错误（必须升级通知）
- ❌ 前置动作（undo/compensate）handler 缺失或执行失败时仍继续续跑（必须拒绝续跑转人工）

## FAQ

- **Q：语义相似度怎么算？没 embedding 怎么办？**
  A：优先用平台 embedding 算余弦相似度；无 embedding 时降级为「同一错误类型前提下的关键词集合 Jaccard 相似度」（中英文均支持：中文按相邻二字组），并在摘要标注 `semantic=fallback`。仅在同一错误类型前提下比较，防止误熔断。**阈值数值以 SKILL.md 为准（单一事实源）**。已知局限：fallback 为词面粒度，近义改写（如「没有响应」vs「无响应」）可能不熔断——由重试上限兜底不会死循环，主方案 embedding 可解。
- **Q：阶段信号平台不给我怎么办？**
  A：默认按 `Processing`；根本未启动按 `Init`，已输出接近完成按 `Finalizing`。阶段定义与推断兜底见 `evals/cases.md` 补充说明 C，推断结果必须在摘要标注。
- **Q：重试次数用完了还失败呢？**
  A：标记 `human_pending` 并输出升级通知；宿主状态契约要求宿主在后续同任务回调进入决策前静默丢弃，不再消耗资源。
- **Q：多个任务同时失败会惊群吗？**
  A：不会。全抖动退避使每次重试时间在 `[0, t_base*2^n]` 内均匀随机，天然打散。
- **Q：最终动作关键词误伤普通任务怎么办？**
  A：中文为子串级匹配（关键词前邻窗口含撤销/取消/勿/不等否定词则豁免，窗口 4 字符），英文为词边界匹配——整体偏保守，如「删除重复项」「必须删除」仍会触发转人工。这是有意取舍：宁可多转人工，不可误重试最终动作。确属可自动恢复的任务，宿主应显式传入 `tx_attr` 覆盖推断。
- **Q：支付类任务超时了怎么办？**
  A：支付/交易类错误一律不自动重试：未命中明确致命错误码的转人工确认扣款状态（含超时子类——无法自动判断是否已扣款，放弃或重试都可能造成资损）；命中 401/400 等致命码的按致命放弃——请求未成功、未产生扣款，无需人工逐单确认。两点边界：① 兜底中英文均识别（payment / transaction declined / 支付 / 付款 / 扣款 / 交易失败）；② prompt 命中最终动作关键词时仍优先转人工（FINAL 判断先于致命分类）。
