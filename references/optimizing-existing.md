# 已有技能优化路径细则

SKILL.md「已有技能优化入口」的展开。用户带着既有技能（zip 或目录）来优化升级时读本文件。以下七节按执行顺序排列，条目末尾括注来源实战（2026-10-24 四次优化：literature-collection / constructivist-ppt / ascii01 / deep-research；2026-10-25 三轮：auto-resume-tasks / huayuhanappt / 四包终版总审）。

## 1. 进入条件与信息盘点

识别信号：用户给出技能压缩包或目录，措辞为「优化 / 升级 / 改进这个技能」，或列出「必须要实现的功能」清单。

动手前完成四件盘点：

1. **解压与命名**：zip 解压到工作区；目录名必须与 frontmatter `name` 一致，不一致时先改名再动（校验器硬门）。
2. **读全量文档**：SKILL.md、references/ 全部、assets 模板——理解声称的契约，这是后面文档对账的基准。
3. **读校验器与门禁**：scripts/ 里的 validate / verify / check / selfcheck 类脚本，弄清每条规则查什么、跳过什么（豁免条件里藏着沉默盲区，如纹理层被结构校验整体跳过——constructivist-ppt）。
4. **画数据流图**：逐脚本列出「读什么 → 写什么 → 谁消费它」。两类断点必须标红：
   - **无消费者的中间产物**（如去重输出全链路无人读，下游仍用未去重源——literature-collection 最重缺陷）；
   - **无生产者的门禁**（校验的文件永不产出，门禁永真或永假）。

## 2. 优化提案规范

用户的历史纠正：「我是问你要功能上的新增，不只是稳定性上的新增」「计划还要再详细一些」。据此定规矩：

- **两栏制**。提案分「修复」（缺陷、一致性、健壮性）与「功能新增」（新能力）两栏分别列出，交付时也分两节汇报。只交修复栏 = 未完成任务。
- **功能新增显式提案**。自主发现的新功能逐项给三要素：落点（哪个文件哪个章节）、验证方式（怎么证明能用）、预估改动面（涉及几个文件）；用选择题让用户挑，不要替用户决定（三次实战均走选择制）。
- **计划细化到落点**。每个需求写明「改哪些文件、加什么命令、怎么验证」，不写「适当增强」「进一步优化」这类无锚点的空话。
- 用户硬需求（「必须要实现的」）直接进清单优先实施，不需要再问。

## 3. 实施纪律

- **预存问题顺手修但单列记录**：版本号不同步、孤儿编号、断链引用这类预存病，修复后单独成节写入交付报告，不混入本次需求改动。
- **新增门禁必须构造必红用例**：证明它在应失败的输入上真的失败（永不失败的门禁等于没有门禁——literature-collection G0 门禁在无 index.csv 时永不达退出 0）。审查存量门禁时同样跑一次必红用例。
- **重复键 fail fast**：索引、合并、导出类脚本遇重复主键报冲突并退出，绝不静默 last-wins（那是丢数据，不是容错）。
- **增量入口主键续编**：给已有数据体系加增量模式（如补录文献）时，编号接存量尾号（`--start N`），从零重编号会与存量冲突——轻则导出报错，重则索引静默丢条目。
- **文档与代码逐项对账**：文件名、键名、子命令清单、参数名、数字口径（键数/条数/行数）逐项核对代码实际行为（literature-collection 一轮抓出 17 处矛盾）。改动后重对账受影响的每一处。
- **API 对照源码核验**：写第三方库用法一律浅克隆对应版本源码读真实签名，不凭记忆写——一次核验可救回整页幻觉 API（ascii01 Remotion 示例全部以 v4.0.538 源码为准）。
- **新增元素重放全部规则**：给存量体系加新元素（新版式、新字段）后，旧门槛豁免会失效，全部校验规则重跑（constructivist-ppt 新版式激活沉睡的 BALANCE 规则）。

## 4. 版本管理

- semver：仅修复 → patch；功能新增 → minor；破坏性变更 → major。
- **三处同步**：frontmatter `metadata.version`、`_meta.json` 的 `version`、`CHANGELOG.md` 顶部条目——校验器已自动比对，不一致会失败。
- 同步更新时间戳类字段：`metadata.updated`、`_meta.json` 的 `publishedAt`、`last_verified` 等。
- CHANGELOG 记本轮全部改动（修复与功能新增分列），这是「保持原打包布局」之外唯一的强制新增文件。
- 打包用 `package_skill.py` 的新参数保持原包形态：扁平包 `--format zip --flat --out-name <原名>-<新版本>.zip`；嵌套包 `--format zip --out-name …`（默认 `.skill` 保持 `<name>/` 嵌套）。node_modules、.venv、.git、__pycache__ 会被自动排除。

## 5. E 维证据适配

技能已存在，RED 无技能基线不再适用，E 维改为双证据：

1. **回归用例全绿**：既有 evals/smoke 用例扩充覆盖本次全部新改动后实跑通过；修复项优先固化为回归用例（防复发）。
2. **与真实历史产物对照**：新输出与用户既有真实产物逐字节或同构对照（literature-collection 题录导出逐字节对照 savedrecs.txt；deep-research export.py 导出与用户手工交付文件同名同大小）。没有历史产物时，构造最小真实数据首测——合成夹具会顺着实现者的假设走，暴露不了真实落点问题。

GREEN 子代理基线退化为走查：新功能从「读 SKILL.md 出发」不借助会话上下文可独立走通。

## 6. 降级预案与二轮深审

- **会话开始即确认子代理可用性**（本环境并发限额与 visual-judge provider 缺失高发）。不可用时的降级：GREEN → 脚本化回归代替；对抗审查 → 按四条清单自省走查；**交付报告显式标注降级**（deep-research 全程无子代理实录）。预案写进计划，不要失败后再临时降级。
- **首轮通过 ≠ 干净**：高价值技能值得二轮深审，两个只读视角分工——「脚本缺陷深审」（边界输入、可达性、静默失败）与「文档一致性 + 功能空白」（声称与行为、缺什么能力）。literature-collection 二轮仍挖出 36 项。
- 修复被证实的问题后，重跑全量回归与 TRACE 五维复查（不只查改过的维度）。

## 7. 终版执行制度（2026-10-25 四包总审实录）

以下七条来自四包终版总审的成功实践，其中前两条是用户原话约束（「四个skill修要隔离，不要把上下文弄混了」「修完记得用那个自检一下」），升格为强制制度：

- **逐对象隔离**：批量优化多个技能时，每个对象配专属子代理，其上下文不出现其他对象，杜绝串味。
- **强制自检三件套**：外部校验器（validate_skill.py）＋包内自检脚本＋新增门禁的必红用例，三者全绿才算修完。
- **主代理独立复现**：交付前主代理亲自复跑全部必红用例与回归，不采信子代理的自述。
- **全绿后强制二轮只读深审**：换视角分工（脚本缺陷线：边界输入、可达性、静默失败；文档一致性＋功能空白线）。终版四包的 HIGH 缺陷几乎全在首轮校验器盲区里。
- **复核更正惯例**：独立复核与在先结论矛盾时，以可复现证据为准，发布更正声明（「本报告替代上一版，以本版为准」）而不是静默覆盖。
- **问答无回答按推荐项继续**：交互提问未获回答时按推荐项执行并在交付记录写明（三次实战均为推荐项落地），不卡死等待。
- **二进制清零清单**（平台拒收二进制时）：纹理转 SVG 源码、生成物移出包、装配时临时栅格化；禁 SVG 直塞 PPTX（产出后缀 .png、内容是 SVG 文本的假媒体，已实测证伪）；交付前 `file` 扫描非文本计数必须为 0。
