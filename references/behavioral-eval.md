# 行为评测协议（RED/GREEN 基线门）与对抗审查

借鉴 skillforge 的 RED/GREEN 门与对抗审查机制，适配本技能五步流程。SKILL.md 第一步（RED）与第四步（GREEN、对抗审查）引用本文件；执行到相应步骤时读本文件。

核心立场：TRACE 的 E 维「结果正确 / 真实增益」靠文档抽查说不清——唯一可靠的证据是**同一个任务，不带技能的 agent 会失败，带技能的 agent 不再失败**。

## RED：生成前的无技能基线

时机：第一步澄清完成后、进入第二步之前。

1. 从需求提炼 1-2 个代表性任务：真实用户口吻，带具体文件名、数据、上下文，不要抽象指令。
2. 派全新子代理（无本技能上下文）执行任务，提示词模板：

```
执行这个任务：
- 任务：<任务原话>
- 输入文件：<路径或"无">
- 把产出保存到：<workspace>/baseline/outputs/
- 完成后用 3-5 条列出你在任务中卡住、做错或拿不准的点
```

3. 逐字记录失败点——它们是技能的测试用例与 description 关键词的原料。
4. 判定：基线**完全不失败** → 技能没必要做，回到澄清或直接劝退；有失败 → RED 通过，失败点记入第四步的 GREEN 验证清单。

降级（无子代理环境）：以新鲜视角逐步推演「不查任何资料我会怎么做」，显式标记不确定点，作为弱基线证据并在记录中标注「推演证据」。

## GREEN：生成后的带技能复跑

时机：第四步客观检查与触发检查之后、逐维判定之前。

1. 同一任务、同样输入，再派一个全新子代理，提示词在 RED 模板上追加：

```
- 先读技能：<技能目录>/SKILL.md，严格按技能指引完成任务
```

2. 判定：与基线失败点逐条比对——**全部消失**＝GREEN 通过；仍有失败＝E 维整改，修复后重跑 GREEN 与全量复查。
3. 记录：任务、基线失败点、复跑结果、消除了哪些失败点，并入轮次记录。

优化已有技能时无第一步基线，GREEN 退化为「新功能从读 SKILL.md 出发可独立走通」的走查，E 维主证据改为回归用例＋真实历史产物对照，见 optimizing-existing.md §5。

## 对抗审查（主观维度的证据来源）

时机：GREEN 之后、逐维判定之前。派一个全新上下文的子代理，唯一任务是**反驳**这个技能：

```
你是一个苛刻的审稿人。读 <技能目录>/SKILL.md 及其引用的配套文件，努力证明它有问题：
1. 找出一条会误导执行者的指令或歧义表述
2. 找出一个该触发却不触发、或不该触发却触发的场景
3. 找出一个技能自己的验证清单没覆盖的失败模式
4. 检查是否有指令自相矛盾
每条给出具体位置（行号或章节）和你构造出的反例；找不到就明说找不到，不要硬凑。
```

处理规则：只修复**被证据证实**的问题（能构造出具体反例的）；「感觉不好」不改；修复后重跑 GREEN 与全量复查。无子代理环境按上述四条清单逐条自省走查并记录。

## 与 TRACE 的映射

- E 维「结果正确 / 真实增益」：以 GREEN 结果为准，行为证据优先于抽查。
- A 维「触发清晰」：引用对抗审查第 2 条的结论与触发 runner 报告。
- R 维「命令可运行」：引用客观检查（validate_skill.py）输出。
